# 需求分析与交互确认规范

配套 `SKILL.md` 阶段 1–4。目标：**用最少的问题问到最关键的信息**，然后让用户确认一份他能看懂的需求总结。

---

## 1. 先提取，再提问

拿到需求先填这张表（内部用，不必展示全表），只问空格子里的 P0 项。

| 维度 | 典型取值 | 优先级 |
|---|---|---|
| 插件名称 | `dsh-xxx-xxx` | P1（但必须确认） |
| 核心问题 | 解决什么痛点 | **P0** |
| 处理的数据 | 会话记录、文件、剪贴板、网络、配置 | **P0** |
| 触发方式 | 对话内、按钮、命令、自动、定时 | **P0** |
| 输出结果 | 文件、界面展示、消息、外部请求 | **P0** |
| 交互布局 | 对话框 / 侧边栏 / 设置页 / 组合 | P1（必须确认） |
| 持久化 | 配置、历史、缓存 | P1 |
| 导入导出 | 格式、范围 | P1 |
| 模块划分 | 单功能 / 多功能 | P1 |
| 预览 / 撤销 / 历史 | 是否需要 | P1 |
| 执行时机 | 自动 / 手动 / 确认后 | P1 |
| 视觉风格 | 简洁 / 卡片 / 深色 / 跟随主题 | P2 |

---

## 2. P0 / P1 / P2 的判断标准

**P0 —— 不问就没法设计**

- 插件具体做什么？
- 读写什么数据、数据从哪来、到哪去？
- 用户怎么触发它？
- 结果以什么形式交付？

**P1 —— 影响交互体验，按复杂度决定问不问**

- 对话框还是侧边栏？要不要设置页？
- 需要预览、撤销、历史记录吗？
- 需要保存配置吗？配置项有哪些？
- 需要导入/导出吗？什么格式？

**P2 —— 视觉与细节，未给就用默认值并说明**

- 配色、圆角、密度、图标风格、动画
- 文案措辞、空状态提示

P2 一律**不要单独开一轮提问**。做法：采用"跟随 DSH 主题 + 简洁"的默认值，在需求总结里写一行"视觉：跟随主题 token，如需特定风格可再调整"。

---

## 3. 分阶段提问（一轮不超过 2–3 个问题）

| 阶段 | 问什么 | 何时跳过 |
|---|---|---|
| 1 | 核心功能、处理的数据、触发方式 | 用户已说明 |
| 2 | 名称候选、交互布局 | 用户已给名称/布局 |
| 3 | 必要细节（格式、范围、默认行为、配置项） | 与插件无关就别问 |
| 4 | 需求总结确认 | 不跳 |

合并原则：同一阶段内彼此独立、且用户一次能答的问题可以合并成一个多选/表单；跨阶段的不要合并。

---

## 4. 选项怎么写才对

**错**：「你有什么需求？」「你喜欢什么风格？」

**对**：给出具体、可判断、带后果的选项。

### 4.1 功能选项（用户只有模糊想法时）

```text
你想做的插件主要解决什么？（可多选，也可以选"其他"自己描述）

A. 界面美化（配色、圆角、密度、字体）
B. 会话导出（Markdown / JSON / 纯文本）
C. 会话管理（批量归档、清理、检索）
D. 网络能力（搜索、抓取、RSS）
E. 文件处理（批量重命名、格式转换、预览）
F. 自定义功能（我来描述）
```

选项要贴合**当前对话上下文**；不要把一个纯 CLI 用户引向"界面美化"。

### 4.2 布局选项

见 `ui-design.md` §2，按功能裁剪后再问。

### 4.3 风格选项（仅涉及 UI 时）

```text
A. 跟随 DSH 主题（推荐）：只用 --dsw-alias-* token，明暗自动适配
B. 简洁实用：中性色、小圆角、紧凑行距
C. 现代卡片：更大圆角、层次阴影、留白充足
D. 深色优先：以深色为设计基准
E. 用户自定义：描述你想要的观感
```

默认 A。选 B/C/D 时要提醒：**必须同时给明暗两套值**，否则深色模式下会刺眼。

### 4.4 默认行为选项

只问与该插件真正相关的：

```text
导出插件 → 导出范围（当前会话 / 选中会话 / 全部）、包含哪些内容（提问/回答/思考/工具）
美化插件 → 是否自动启用、是否记住选择、能否一键还原
搜索插件 → 是否自动联网、结果条数上限、是否缓存
```

---

## 5. "你决定"的处理

用户说"你决定 / 不用问我 / 你看着办"时：

1. 视为授权在**非破坏性范围**内自主决策。
2. 仍然需要遵守：不擅自加功能、不擅自联网、不擅自改用户已有项目。
3. 在需求总结里逐条列出采用的默认值，标注"（默认，可改）"。
4. 名称与布局**仍然给出你的选择和理由**，而不是默默决定 —— 用户可以在总结确认阶段反驳。

---

## 6. 需求总结模板

```text
【需求总结】

插件名称：dsh-xxx-yyy
主要功能：<一句话>
功能模块：<模块1>、<模块2>、<模块3>
交互方式：<区域> 负责 <职责>；<区域> 负责 <职责>
配置需求：<有哪些配置项，默认值是什么；或"无配置">
UI 风格：<跟随主题 / 具体描述>
数据处理：<读什么、写什么、是否离开本机、是否持久化>
关键约束：<平台、版本、仅本机、只读等>
默认值（可改）：<列出你替用户决定的非关键项>

确认无误我就进入架构设计；需要改的地方直接说。
```

写不出来 = 需求还不够清楚，继续问。

## 7. 典型需求 → 需要补的问题

| 用户说 | 已足够 | 还需问 |
|---|---|---|
| "做个聊天记录导出插件" | 功能、数据 | 导出格式、范围、是否含工具调用、布局 |
| "做个界面美化插件" | 功能 | 美化哪些区域、几套预设、是否可关闭、入口位置 |
| "做个会话搜索插件" | 功能 | 搜什么范围、是否联网、结果怎么展示 |
| "做个 dsh-foo 插件，导出 Markdown" | 名称、功能、格式 | 导出范围、入口位置、是否需要配置 |
| "做个插件" | 什么都没有 | 先问功能（P0） |

---

## 8. 需求冲突的处理

常见冲突：

- "导出全部聊天记录" + "不要碰任何隐私数据" → 指出矛盾，让用户选：只导出当前会话 / 导出时脱敏 / 明确接受本地读取。
- "自动执行" + "每次先让我确认" → 二者只能选一，说明差异（自动 = 无打扰但有风险；确认 = 安全但打断）。
- "支持所有 DSH 版本" + 用到新 API → 说明无法同时满足，给出版本下限。

处理方式：**陈述冲突 → 给 2–3 个可选解法 → 让用户选**，不要自己悄悄选一个。

---

## 9. 不该问的问题

- 用户已经说过的（重复询问是最明显的失误）。
- 与插件无关的（做导出插件却问配色偏好）。
- 纯实现细节、用户无从判断的（"用不用 ResizeObserver？"）。
- 需要你先查文档才能回答的（自己查，别问用户）。
- 为了"流程完整"而问的（每个插件都问一遍"要不要撤销"）。

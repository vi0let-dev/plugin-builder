# 交互布局设计规范

配套 `SKILL.md` 阶段 3 与阶段 5。回答一个问题：**这个插件该长在 DSH 的哪个位置？**

所有 slot 名都必须在动手前用 `cordis_inspect_query`（platform `client`、provider `Slots`、method `listSubTree`）现场确认。本文件给的是**选型逻辑与已核实的候选**，不是永久有效的地图。

---

## 1. 先判断：这个插件需不需要 UI

| 形态 | 判据 | 例子 |
|---|---|---|
| 无 UI（Host-only） | 作用对象是模型的行为或后台任务 | 注册一个工具、给提示词加一节、接一个 MCP 服务 |
| 轻量 UI | 只有一两个开关或一次点击 | 一个主题切换按钮 |
| 完整 UI | 有列表、表单、多项配置、状态展示 | 会话选择 + 导出配置 + 下载 |

无 UI 是完全合法的交付形态，但**必须在需求总结里明说**："这个插件没有界面入口，通过工具 `<name>` 触发"——否则用户会以为插件没装上。

---

## 2. 六种布局选项

问用户时按功能裁剪，不要六个全抛。

### A. 对话框交互
在会话里直接操作：一句话触发、参数用自然语言给、结果回到对话里。

- 适合：快速执行、参数少、即时反馈、轻量功能
- 不適合：多步骤流程、需要长时间停留的状态
- 实现取向：注册工具（`ctx.tools.register`）或输入区入口（`conversation.input.dock`）

### B. 侧边栏交互
左栏提供一个入口或一组操作。

- 适合：高频使用、需要常驻、多功能集合
- 候选 slot：`sidebar.panellist`（图标）、`sidebar.footer.action`（底部动作）、`sidebar.workspaces.session.menu.item`（会话右键菜单）
- 注意：侧边栏空间紧张，别塞长文案

### C. 独立设置页面
设置面板里一整页。

- 适合：复杂参数、多项配置、长期偏好、完整管理界面
- slot：`settings.section`（整页，可配 `label` 作为导航名）
- 注意：设置页不是"操作页"，长时间运行的任务要有进度与取消

### D. 对话框 + 设置页面
对话负责快速执行，设置页负责长期配置。

- 适合：日常用默认值一键搞定，偶尔需要调参
- 要写清楚哪些配置在设置页、哪些能用一句话覆盖

### E. 侧边栏 + 设置页面
侧边栏做入口与状态，设置页做参数。

- 适合：需要"看见状态 + 随时进入 + 可配置"的常驻功能

### F. 用户自定义
用户描述形态（浮层、面板、聊天内嵌卡片、独立页面……）。此时按描述去找 slot，找不到就告诉用户"当前 DSH 没有该位置的扩展点"，并给出最接近的方案。

---

## 3. 组合式方案怎么写

复杂插件允许三段式，但必须逐区域说明职责：

```text
对话框：一句话触发导出（"把这个会话导成 Markdown"）
侧边栏：导出入口 + 最近三次导出记录
设置页：默认格式、默认包含项、文件名模板、是否包含工具结果
```

判断是否需要多区域的三个信号：

1. 功能不止一个，且使用频率差异大
2. 存在"长期配置"与"临时操作"两类需求
3. 需要展示持续状态（进行中、上次结果、错误）

三个都没有 → 单区域就够，别为了显得完整而加区域。

```text
cordis_inspect_query(platform: "client", provider: "Slots", method: "listSubTree",
                     input: { root: "settings.section" })
```

返回该 slot 的 catalog、占用者、注册参数与 props 形状。

## 5. 视觉规范（P2，默认值优先）

### 必须遵守

1. **颜色只用主题 token**：`--dsw-alias-*`、`--dsw-specific-*`（见 `dsh-plugin-api.md` §5）。写死 `#fff` 在深色模式下等于坏掉。
2. **明暗双套**：任何自定义取值都要在 `[data-theme="dark"]` 或媒体查询下给出对应值。
3. **文案走 locale**，不把中文硬塞进组件；至少 zh + en。
4. **匹配宿主排版**：字号、行高、间距向 DSH 同类型页面看齐，别自创一套密度。
5. **不覆盖全局**：不给 `body`、`*` 写样式；选择器挂在自己的 `data-plugin` 前缀下。

### 风格预设的写法

```text
A. 跟随主题（默认）：零硬编码颜色，只用 token
B. 简洁实用：token + 小圆角 + 紧凑行距
C. 现代卡片：token + 大圆角 + 层次背景
D. 深色优先：以深色基准设计，再给亮色覆盖
```

选 B/C/D 时在需求总结里写一句："已同时定义明暗两套取值，主题切换时自动适配。"

### 动效

默认不加。要加就：只在用户可见的状态变化上（展开、保存成功），时长 ≤ 200ms，尊重 `prefers-reduced-motion`。

## 6. 交互契约（容易被忽略但必须实现）

| 场景 | 要求 |
|---|---|
| 加载中 | 有可见的进行中状态，不要"点了没反应" |
| 失败 | 显示原因 + 可重试；失败不静默 |
| 空状态 | 明确告诉用户"还没有数据"以及下一步能做什么 |
| 危险操作 | 二次确认，或提供撤销 |
| 长列表 | 分页或虚拟化，别一次渲染几千条 |
| 键盘 | 弹窗支持 Esc 关闭，焦点可见 |
| 无障碍 | 按钮有可访问名称，开关用 `role="switch"` + `aria-checked` |
| 卸载 | 移除自己加的 style、监听、定时器、DOM 节点 |

---

## 7. 常见布局误判

| 误判 | 后果 | 正确做法 |
|---|---|---|
| 把设置页当成操作台 | 用户每次操作都要进设置 | 高频操作放对话/侧边栏，设置页只放参数 |
| 往 `conversation.composer.dock` 塞大块 UI | 挤压输入区 | 那里只放一行内的紧凑元素 |
| 用 `shell.overlay` 做静态徽标 | 浮层挡交互 | 用有分配空间的 slot |
| 替换 app root / 追加第二个 app | 整个界面崩 | 只能用 slot |
| 读别的插件的 DOM 估算位置 | 升级即碎 | 选已分配空间的 slot |
| 所有插件都配侧边栏 + 设置页 | 界面噪声 | 按需，纯工具插件可以零 UI |

## 8. 布局方案确认话术

```text
基于"<功能>"，建议这样分布：

- <区域 1>：<职责>（落在 <slot>，因为 <理由>）
- <区域 2>：<职责>
- 视觉：<跟随主题 / 具体风格>，明暗双套

备选：<更简单的方案>（如果只想最小可用）
确认这个布局，还是换一种？
```

不要只给一个方案就让用户"确认"——至少给一个更轻的备选，让用户能判断复杂度。
